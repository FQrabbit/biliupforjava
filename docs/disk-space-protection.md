# 磁盘空间保护

程序默认每秒检查工作目录和实际本地 H2 数据库所在磁盘，同一磁盘只统计一次。任一磁盘使用率达到 **98%**，或可用空间不超过 **2 GiB**，就停止接收新业务并开始收尾

## 进入保护后

- 新上传、投稿、统计、文件处理等业务停止进入，已排队任务停止消费
- 正在执行的任务收到停止请求，数据库事务尽力正常提交或回滚；不等待整段大文件全部上传完毕
- 确认操作收尾后正常关闭本地 H2；使用远程数据库时，只关闭本程序连接，不关闭远端数据库服务器
- 保留不依赖业务数据库的保护页、空间检查和必要通知；日志停止常规文件写入
- 录播姬和 blrec 的新录制事件返回 HTTP 503，表示未接收，不继续写入本地队列

保护页地址是原访问地址下的 `/disk-protection`，使用原有账号密码。启动前发现空间不足时也会提供保护页，不先打开业务数据库或执行数据库迁移。原端口切换到保护服务期间连接可能短暂中断

## 如何恢复

1. 自行检查并暂停外部录制器，释放磁盘空间
2. 等待所有受保护磁盘使用率不高于 **95%**，并且可用空间至少 **10 GiB**，连续满足 **30 秒**
3. 在保护页点击“重新检查并恢复工作”

程序不会因为空间恢复就自动开启业务。已经记录的保护状态会保留到业务核心成功启动；简单重启不能绕过手动恢复要求。重新启动业务核心期间可以稍后刷新页面

如果保护页显示异常，应先处理关闭失败、目录丢失或空间检测失败等原因，不能把“停止接收任务”理解为“数据库已经安全关闭”

## 参数

在原有 `application.yml` 中合并以下配置，修改后重启生效。保护逻辑在业务数据库初始化之前使用这些配置，因此不将参数保存在业务数据库中

```yaml
record:
  disk-protection:
    stop-percent: 98
    stop-bytes: 2147483648       # 2 GiB
    resume-percent: 95
    resume-bytes: 10737418240    # 10 GiB
    interval-ms: 1000
    stable-ms: 30000
    probe-timeout-ms: 800
    drain-ms: 30000
```

恢复阈值需要比触发阈值留出更多余量。小容量磁盘若无法提供 10 GiB 可用空间，需要按实际容量调整参数。每秒检查表示在下一次成功探测时识别阈值，不能保证跨线瞬间就完成关闭

通知复用“工作目录空间预警”事件已有的推送规则和渠道，配置会提前缓存在内存。保护期间发送通知不写投递记录，通知失败不会阻塞保护；刚启动就处于保护模式时，数据库尚未打开，只能通过保护页和控制台查看状态

工作目录中的 `.biliup-disk-protection` 是很小的保护状态文件，不是容量预留文件，请通过保护页恢复。不要通过手工删除该文件跳过检查

程序运行目录还会保存一个很小的 `.biliup-storage-*.properties` 文件，登记已确认的存储目录与磁盘，供下次启动识别目录丢失或挂载变化。程序目录只读时，可通过 `record.disk-protection.history-file` 指定其他可写的持久位置；建议放在受监测挂载之外。登记文件仅在目录首次确认时更新，不随每秒探测持续写入

## 能力边界

程序不会自动停止外部录制器，也不会自动删除录像腾空间。外部程序仍可能把剩余空间迅速占满；本功能降低风险，不能保证数据库绝对不会损坏，也不能保证最后一次状态保存一定成功

没有建立应急容量预留文件。低空间时不会临时生成全量数据库备份或运行数据库压缩

录制器如果不重试被拒收的事件，部分录制记录可能漏记，不能保证恢复后自动补齐。已发出但结果不明的投稿需要先核对线上状态，不能盲目重复提交

本机容量检查不能确认远端 MySQL 或远程 H2 所在服务器的磁盘状态。网络盘、Docker 挂载和底层文件系统故障也需要单独排查
